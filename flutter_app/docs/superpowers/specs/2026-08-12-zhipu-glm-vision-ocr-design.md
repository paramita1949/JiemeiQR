# 智谱 GLM 视觉 OCR 接入设计

## 目标

将智谱视觉模型作为独立 OCR 提供方接入 QRSCAN，同时支持：

- 订单拍照识别；
- 交货计划截图识别。

参考脚本 `glm_vision_mcp.py` 仅用于确认智谱接口、请求结构、响应结构和模型回退规则。APP 直接请求智谱 API，不依赖 Python、MCP 或电脑端进程。

## 配置与界面

沿用 APP 现有“横向提供方卡片 -> 仅显示当前提供方配置”的交互：

- 新增提供方 `zhipu`，界面名称为“智谱”；
- 配置项为“智谱 API Key”和模型下拉框；
- 内置模型：
  - `glm-4.6v-flash`，默认首选；
  - `glm-4v-flash`；
- 两个模型使用现有模型预设管理和选择方式，不改变其他提供方界面；
- 配置写入现有 `ai_ocr_config.json`，不在源码中保存真实密钥；
- 旧配置缺少智谱字段时，使用空密钥和默认模型，原提供方选择不受影响。

`AiOcrConfig` 增加智谱提供方常量、API Key、当前模型、模型预设列表及对应状态 getter，并同步扩展序列化、反序列化、复制和缺省配置。

## 服务结构

采用小范围独立适配，不重构现有 OCR 提供方：

1. `ZhipuVisionClient`
   - 请求固定接口 `https://open.bigmodel.cn/api/paas/v4/chat/completions`；
   - 使用 `Authorization: Bearer <API_KEY>`；
   - 将本地图片编码为 MIME 正确的 base64 data URL；
   - 发送 OCR 提示词和图片；
   - 解析 `choices[0].message.content`；
   - 清理外围 Markdown JSON 代码块；
   - 统一转换智谱 HTTP/API 错误。
2. `ZhipuWaybillOcrService`
   - 复用现有订单图片预处理、OCR 提示词、`WaybillOcrDraft`、商家历史匹配、空结果判断和诊断日志；
   - 不改变批次匹配、重复明细合并、库存校验、运单号唯一性和保存流程。
3. `ZhipuDeliveryPlanOcrService`
   - 复用现有交货计划提示词和 `DeliveryPlanOcrDraft`；
   - 库位仍由 APP 本地基础资料匹配，不让模型推断库位。
4. 两个现有配置路由器增加明确的智谱分支；Gemini、魔搭、飞桨的现有路由和回退行为保持不变。

## 请求与模型回退

首轮使用用户当前选择的模型。模型尝试顺序去重后最多为：

1. 当前选择模型；
2. 另一个内置 GLM 视觉模型。

请求使用 OpenAI 兼容多模态消息：

```json
{
  "model": "glm-4.6v-flash",
  "messages": [
    {
      "role": "user",
      "content": [
        {"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}},
        {"type": "text", "text": "现有 OCR 提示词"}
      ]
    }
  ],
  "thinking": {"type": "disabled"},
  "stream": false
}
```

以下情况切换到另一个模型：

- HTTP 429；
- API 错误码 `1305`；
- 当前模型过载、暂不可用或返回无有效结果。

鉴权失败、参数错误等非模型可恢复错误直接显示中文错误，不使用另一模型掩盖配置问题。两个模型都失败时，错误信息包含两次尝试的简要原因，不包含 API Key。

## 订单数据流

1. 用户选择“智谱”并拍摄或选择运单图片；
2. APP 按现有规则预处理图片；
3. 智谱服务使用现有订单 OCR 提示词请求首选模型；
4. 必要时自动尝试另一个 GLM 模型；
5. 返回内容解析为现有 `WaybillOcrDraft`；
6. 执行现有商家历史匹配并进入原订单确认、批次匹配、库存校验和保存流程。

## 交货计划数据流

1. 设置页选择的智谱配置可直接作为默认识别提供方；
2. 交货计划拍照/相册面板沿用现有临时提供方和模型选择方式，加入“智谱”及两个模型；
3. 智谱服务使用现有交货计划 OCR 提示词；
4. 返回内容解析为现有 `DeliveryPlanOcrDraft`；
5. APP 继续执行现有本地产品和库位匹配及确认流程。

## 错误与日志

- 缺少密钥：`缺少智谱 API Key`；
- 鉴权失败：提示密钥无效或无调用权限；
- 429/1305：先尝试另一模型；
- 响应结构、空文本或 JSON 无效：使用当前 OCR 场景的中文错误；
- 路由和诊断日志提供方记为 `zhipu`，记录实际成功模型，不记录密钥或完整图片数据。

## 测试

按 TDD 增加或扩展测试：

- 智谱配置默认值、保存/加载、旧配置兼容；
- 设置页提供方卡片、字段显示、模型选择和保存；
- 请求 URL、Bearer 头、模型、图片 data URL、提示词和响应解析；
- 首选模型成功；
- HTTP 429、错误码 1305 和无有效结果时回退；
- 两个模型都失败时的错误；
- 订单路由、订单草稿解析和商家历史匹配；
- 交货计划路由、草稿解析及拍照面板临时选择；
- 现有提供方无行为回归。

最终顺序运行聚焦测试、完整 `flutter test` 和 `flutter analyze`，不构建 APK。

## 非目标

- 不把参考 MCP 脚本打包进 APP；
- 不复制电脑环境变量或真实 API Key；
- 不把智谱模型放入魔搭配置；
- 不重构为通用供应商插件框架；
- 不改变 OCR 之后的订单、库存或交货计划业务规则。
