# 新多模型 AI 平台接入设计

## 目标

在现有 AI 配置中新增一个独立的多模型平台，使订单拍照识别和交货计划拍照识别都能通过同一份平台凭据与模型配置工作。保持现有平台行为不变，不进行通用供应商框架重构。

## 用户体验

- AI 配置页新增第 4 个平台卡片。
- 选择后填写访问令牌，并从模型列表选择当前模型。
- 模型列表支持新增、切换和删除，适合平台持续增加模型的特点。
- 默认预置一个已经验证支持图像输入的模型。
- 保存后，订单识别和交货计划识别都立即路由到该平台。
- 错误提示使用中文，区分缺少配置、鉴权失败、模型不支持图片、额度或限流、无有效识别结果等情况。

## 配置与持久化

在 `AiOcrConfig` 中增加独立字段：

- 平台 provider 常量。
- 访问令牌。
- 当前模型标识。
- 模型预设列表。

`toJson`、`fromJson`、`copyWith`、缺省配置和配置文件兼容逻辑同步扩展。旧配置文件缺少新字段时使用空令牌和默认模型，不影响原有平台选择。

## 服务结构

采用独立平台适配器，不复用或改写现有平台服务：

1. 新增共享的图文请求构造与 HTTP 调用单元，负责：
   - 使用 OpenAI 兼容的聊天补全接口。
   - Bearer Token 鉴权。
   - 将本地图片编码为 data URL。
   - 发送文本提示词和图片内容。
   - 读取 `choices[0].message.content`。
   - 将 HTTP 状态和接口错误转换为中文业务异常。
2. 订单适配器沿用订单现有提示词、图片预处理、JSON 解析、商家名称匹配和诊断日志。
3. 交货计划适配器沿用交货计划现有提示词和 JSON 解析。
4. 两个配置路由器根据 provider 选择新适配器；其他 provider 的顺序和回退规则保持不变。

## 请求与响应

请求采用平台的 OpenAI 兼容格式：

- `model` 使用用户当前选择的完整模型标识。
- `messages` 中用户内容包含一段 OCR 提示词和一个 `image_url` data URL。
- 使用适合结构化抽取的低温度配置。
- 设置足够的输出 token 上限，避免 JSON 因长度限制被截断。

响应先检查 HTTP 状态与接口 `error`，再读取文本内容。文本允许被 Markdown JSON 代码块包裹，清理后交给现有业务模型解析。

## 配置界面

- 现有横向三等分平台卡片调整为可换行或可横向滚动的四平台布局，避免小屏卡片过窄。
- 新平台字段沿用现有模型选择组件，包含令牌输入、当前模型选择、新增模型和删除模型。
- 自动保存、显式保存、已配置状态和字段校验覆盖新平台。
- 不新增模型联网搜索或自动拉取列表；用户通过完整模型标识管理列表，保持实现轻量且稳定。

## 测试

新增或扩展以下测试：

- 配置序列化、反序列化、旧配置兼容和 provider 保留。
- 配置页面显示第 4 个平台，切换后展示正确字段并保存模型列表。
- 订单路由选择新服务。
- 交货计划路由选择新服务。
- 图文请求包含正确的模型、Bearer Token、提示词和 data URL。
- 成功响应解析、空响应、鉴权错误、限流/额度错误和非图片模型错误。
- 运行 Flutter 静态分析和完整测试集确认无回归。

## 非目标

- 不自动抓取平台全部模型。
- 不测试或筛选每个模型是否支持图片。
- 不重构现有所有平台为统一插件框架。
- 不在应用中内置用户访问令牌。
